# Limit reset: legitimate routes (2026-11-19)

Read-only research. No reset used, no POST/PUT/PATCH/DELETE, no request with altered identity, no Bright Data, no token printed. Only the installed CLI bundle (Claude Code 2.1.327, `/Users/ahmed/.local/share/claude/versions/2.1.327`, read with `strings`) and PixelSwitch sources were read. Founder order recorded: "you absolutly do not execute a reset": no reset by any route from this work; every route below ends with the owner choosing and clicking.

## 1. How "surface" is decided
- Listing call: `GET /api/oauth/usage?cedar_ember=1&skip_spend=1` through Claude Code's shared HTTP client. The call itself sets only `Content-Type: application/json`, a 5 s timeout and the OAuth bearer. The client's standard identity headers are `x-app: cli` (or `cli-bg`), `User-Agent: claude-cli/<version> ...`, `X-Claude-Code-Session-Id`, plus `anthropic-beta`. No `surface` parameter is sent on the cedar_ember listing. (A `surface=` query exists only on the separate starry_waterfall credit-offer read.)
- Reset POST: `POST /api/organizations/{organizationUuid}/reset_rate_limits`, body `{program:"cedar_ember", grant_id, request_id}`, same client, same headers, bearer refreshed on 401. Nothing client-chosen called "surface" is in the body.
- The response carries `event_props.surface` with enum `claude_ai | claude_code_cli | unknown`, and `ineligible_reason` has a `surface` value. So surface is returned by the server, not stated by the client. Inference (not proven): the server derives it from the request's client identity (x-app/User-Agent) and the login source (the CLI also checks that the login source is claude.ai before it advertises the reset).
- Evidence for the gate: PixelSwitch's token for beeco1@pixelventures.ai got `eligible=false, reason "surface", grants []` while the owner says beeco1 has a reset available now. Same token class, same account, different caller: the caller decides. Another account (ahmed@pixelventures.ai) returned 403 on the same call (cause unread).

## 2. Can the genuine CLI do it?
- `/limit-reset` is a `local-jsx` (interactive Ink screen) command, hidden, with no `supportsNonInteractive`. So `claude -p "/limit-reset"` is not a supported path; it needs a real terminal (a pty). Unproven: whether a pty-driven run would work.
- Enabled only when logged in with the `user:profile` scope AND the server config object `tengu_cedar_ember` has `enabled: true` for the account. If the flag is off the command is absent (isEnabled false). The same flag could be off for some accounts.
- Flow, from the strings: it lists first, with argument hint `[fable|full|5-hour|weekly]`. Screens: "Which reset do you want to use?", then "Use a {kind}?" with the effect text, buttons "Yes, use my {kind}" and "No, keep it". Also asks "use it anyway?" if no limit has been reached. So an explicit choice and a confirmation precede any use; the argument only pre-selects the kind. No grant-id argument. Exception unverified: a bare argument may skip the chooser, but the confirm screen exists. Treat any invocation as dangerous: the confirm screen is the only guard.
- Account scoping: PixelSwitch does NOT scope a CLI run per account. `ClaudeProcessEnvironment` only sets PATH and HOME; `ClaudeCredentialsFile` says CLAUDE_CONFIG_DIR is not honored by PixelSwitch; `auth login` writes the one Keychain item `Claude Code-credentials`. So "CLI for a chosen account" means PixelSwitch makes that account the active login (its existing switch), then the owner runs the CLI in a terminal. Using a per-account CLAUDE_CONFIG_DIR is not tested.
- What it prints: lines such as "Reset used · N left", "Couldn't confirm the reset went through...". Listing alone does not print grants outside the chooser.

## Routes, ranked
1. (c) Open claude.ai/settings/usage in the default browser. Owner once: be signed in per account (sign out/in or profiles per account). Per reset: pick the account, open the page, read the offer, click the page's own button (about 3 clicks plus an account switch). Breaks: browser holds one claude.ai session at a time; wrong account clicked; page layout changes. Unproven: nothing technical; it is the page the owner already sees the offers on.
2. (b) Embedded claude.ai page per account in PixelSwitch (WKWebView with a separate `WKWebsiteDataStore(forIdentifier:)` per account). Owner once: sign in to claude.ai in each of 7 accounts (email link or Google; Google sign-in inside an embedded web view is often blocked). Per reset: pick account tab, click the page's button, 2 clicks. Breaks: login blocked or CAPTCHA in a web view, session expiry per account, Cloudflare. Unproven: that claude.ai accepts the embedded web view's login and shows the same offers. Nothing is imitated; it is the genuine page.
3. (a) Genuine CLI in a terminal. Owner once: none beyond existing logins, if the `tengu_cedar_ember` flag is on per account (unknown). Per reset: PixelSwitch switches the active account, owner opens a terminal, runs `claude`, types `/limit-reset`, reads the chooser, picks and confirms (about 5 steps). To "show the offers first without using one" the owner stops at the chooser or answers "No, keep it"; PixelSwitch cannot show them itself without driving the confirm flow, which is not recommended. Breaks: command hidden if flag off; surface "claude_code_cli" may not carry the Fable reset; changing active account interrupts running sessions. Unproven: that the CLI lists beeco1's reset at all (the web-only "surface" grants may be claude.ai-only).

Ranking reason: (c) works today with zero build and zero risk; (b) is nicer but its login is the main risk; (a) is the heaviest and depends on a hidden flag and a surface the server may not offer.
