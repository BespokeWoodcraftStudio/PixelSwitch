# The usage "API Rate Limited" banner, 2026-10-16

Written 2026-10-16, for PixelSwitch 1.9. The evidence scripts are in `2026-10-16-usage-429/scripts/` (see the README there).
No Anthropic endpoint was called to produce any of this; every number comes from PixelSwitch's own log
(`~/Library/Logs/PixelSwitch-app.log` and its two rotated copies, 2026-10-06 23:22Z to 2026-10-16 14:08Z).

## What the founder saw

Cards for ahmed@pixelventures.ai, ahamade@gmail.com and ahmed@bespokewoodcraftstudio.com showed "API Rate Limited. Try again
later." for an hour at a time, then again. Re-authenticating an account fixed the login but not the card. A dead-looking
account still looked switchable, and trying to switch to it failed.

Claude Code itself was never rate limited by any of this. Sessions on ahmed@bespokewoodcraftstudio.com spent $371 on
2026-10-16 while its card showed the banner. The 429s are on Anthropic's usage lookup (`/api/oauth/usage`) and the profile
lookup (`/api/oauth/profile`) only.

## The mechanism

Anthropic answers roughly the fourth refused (401) call on the same access token within about an hour with 429 and
`Retry-After: 3600`. All 49 of the 49 429s in the log had at least one 401 on that account since its last 200. Healthy tokens
were never refused: claude@bespokewoodcraftstudio.com had 748 answers of 200 and no 429, at up to 13 requests an hour.
Volume is not the cause.

The 429 is decided before the token is even checked: the median reply time is 24 ms for a 429, 114 ms for a 401 and 346 ms
for a 200 (49, 568 and 2,889 requests).

One rule fits the whole 9.5 days: count the failed calls on an account in the previous hour (usage 401s plus profile 401s).
With 2 or fewer, no request out of about 3,200 got a 429. With 3, 4 of 222 did. With 4 or more, 45 of 47 did. With profile
401s counted, a one-hour estimate with a threshold of 4 predicts all 49 429s. The exact server rule is approximate, not proven.

## What was PixelSwitch's doing

PixelSwitch kept sending tokens it could have known were dead.

1. **The live login after it expires while Claude Code is idle (41 of the 49 429s).** Claude Code renews its login only when a
   session makes a model call. On 2026-10-13 there were no sessions all day, so claude@pixelventures.ai's token sat expired
   for 24 hours. PixelSwitch sent a usage request every 5 minutes and, through `reconcileLiveLogin`, a profile lookup every
   5 minutes, with that expired token (454 profile 401s in total). Never looking at `expiresAt` was the whole problem.
2. **Saved logins whose refresh grant the server had already refused.** ahmed@pixelventures.ai has been dead since
   2026-10-12 15:53Z and ahamade@gmail.com since about 2026-10-10 19:01Z. Every round-robin visit cost a usage 401 and a
   refresh request answered `invalid_grant` (473 such lines), forever.
3. **Switch attempts and the saved-login audit sent profile lookups with expired tokens before checking expiry.** Each of the
   founder's five switch attempts on 2026-10-16 (four to ahmed@pixelventures.ai between 13:42:50 and 13:44:24Z, one to
   ahamade@gmail.com at 14:05:58Z) cost one more profile 401.
4. **The round-robin sped itself up.** Each refresh cycle reads the active account plus ONE other, taken in turn from the
   accounts that are not parked. When an account is parked, the list gets shorter, so the remaining dead backups are visited
   more often. For five days the two dead backups were polled exactly every 20 minutes (no four failures ever fell inside 60.0
   minutes across 443 failures), which kept them just under the limit. At 06:53:08Z on 2026-10-16 an auto-switch moved
   to claude@bespokewoodcraftstudio.com, and the switch ran an extra refresh cycle: ahamade@gmail.com was asked at 06:53:11
   (15 minutes after 06:38) and ahmed@pixelventures.ai's next visit moved to 06:58, 15 minutes after 06:43, which drew the
   first 429. Once that account was parked, the other dead backup was visited every 15 minutes, drew its own 429 at 07:18, and
   from then on each park sped up the other account. Gaps of 10, 15 and even 5 minutes appear after that.
5. **The "delegated refresh" never refreshed anything.** For an expired live token PixelSwitch ran `claude auth status`
   hoping Claude Code would renew the login, then asked again with the same token. It ran 13 times and recovered 0 times.
   Example: `04:03:02.216 Delegated refresh completed`, then `04:03:02.377 HTTP 401`.

## What was refuted

- **"The server got stricter on 2026-10-16 between 04:00Z and 07:00Z."** This was the first diagnosis. Two skeptic passes
  refuted it. Before 06:53Z both dead backups were polled on a strict 20-minute cadence, and "up to 4 per hour" was a count
  of both ends of a closed hour. After the auto-switch the gaps fell to 5 to 15 minutes, and the 429s followed. The same one
  rule explains both periods, so the server did not need to change.
- **"A wait of 20 minutes between requests is slow enough, so volume is the cause."** Volume is not the cause. A healthy token is
  never refused.
- **"The GM experiment at about 14:50Z will tell per-token from per-account."** It cannot: by then the 13:48 block has expired
  and the failure count has decayed under the threshold, so both models predict a 200.
- Ruled out (measured): bursts (at most 2 requests in 60 seconds, the 401 then retry pair), park violations (zero), Claude
  Code, Claude.app, claude-mem and PixelDirector polling on a timer, and the Beeco Mac (none of the five founder accounts is
  on it; its only 429s were on one account that needs signing in again, the same dead-login pattern, lane-reported).
- `claude auth status` itself adds no failing request. Its median run is 147 ms with a stale live token and 279 ms with a fresh
  one, so it seems to skip the network when the token is expired.

## What is outside PixelSwitch

- Anthropic's limiter, which answers repeated 401s with a one-hour 429.
- Claude Code not renewing a login nobody is using.
- Whoever revoked the two refresh grants (see "Still unknown").

## Why the banner stuck

1. **A 401 wiped the reading first.** An expired token has `keepsLastReading == false`, and so did a refused grant, so the card
   lost its numbers.
2. **The honest message was then overwritten.** On the next visit the old error was cleared. The request drew a 429, and
   because no reading was left, the card showed "API Rate Limited. Try again later." in place of "Session expired.
   Re-authenticate (↻) to fix."
3. **It stayed up for an hour.** Only accounts picked as targets had their message cleared, and a parked account is never a
   target. Every hour the same dead token earned a fresh 429.
4. **The park belonged to the account, not to the token.** Re-authenticating, switching to the account or the live login being
   renewed cleared nothing. The only thing that cleared it was removing the account. ahmed@pixelventures.ai was
   re-authenticated at 13:44:54Z and first read at 13:53:04Z; ahamade@gmail.com was re-authenticated at 14:07:08Z, became
   the live login, was never read before the founder switched away at 14:20:27Z, and stayed parked until 14:48:02Z.
5. **A dead account still looked switchable.** The 429 state was not marked expired, so `isSwitchable` said yes, and each
   switch attempt sent one more profile lookup with the dead token.
6. **While the active account was parked, auto-switch was blind on it.** Re-authenticating also silently made that account
   the live Claude Code login.

## The fix (PixelSwitch 1.9)

A pure guard, `PixelSwitch/Services/UsageRequestGuard.swift`, decides before ANY request carrying an access token whether it
may go. It remembers tokens by a short non-reversible fingerprint (SHA-256, first 16 hex characters; a log line shows at most
the first 8). The rules:

- A token that got a 401 is never sent again until the account's stored or live token changes. This also catches tokens
  revoked before they expire, and credentials with no `expiresAt`.
- A token whose `expiresAt` is known and is past, or within 60 seconds, is never sent. A missing `expiresAt` is allowed (the
  rule above stops it after one 401).
- A 429 park holds only while the account still has the token it was earned on. A new token is asked at once.
- After a 401 or a 429 on a token, nothing else is sent with it for 20 minutes, however many accounts are being polled. This
  removes the round-robin speed-up.
- An account the server refused a refresh grant for (`needsReauth`, saved across a relaunch as account ids only) gets no
  usage, profile or refresh request until its token changes. It is skipped in polling, cannot be switched to, and its card
  says to sign in again.
- The live login is never silently dropped. An expired or refused live token sends nothing, the card keeps the last reading
  and says "Waiting for Claude Code to renew this login. It renews the next time a session runs.", and the moment Claude Code
  renews it (the fingerprint changes) the account is read again.
- A saved login that is expired or refused is renewed in place FIRST, then asked once with the new token.

Every path goes through it: the polling cycle, the verification read auto-switch takes before it switches, the card's Retry,
the command line and MCP refresh (they run the same cycle), the live-login ownership check every cycle, the saved-login audit,
switch validation (which now checks expiry and renews BEFORE the profile lookup), the profile checks inside a switch and a
sign-in capture, and the check after a renewal. Every 401 from the usage or profile endpoint is recorded by token.

One hook, `noteCredentialChanged(for:)`, is called wherever an account's stored or live credential changes: a re-authentication
or sign-in capture, the live login saved over a backup (compared by Claude token, not the whole 26 KB credential, which holds
this Mac's MCP logins and changes hourly without a Claude token change), a renewal in place, a switch (for the account switched
to and the one switched from), and an account becoming active. It clears that account's park, refusal, needs-reauth flag,
cool-down and card message, and has the account read next cycle, ahead of the round-robin.

Honest messages, in all five languages: "Usage reading paused until 14:48. Claude Code itself is not affected." on a 429 (the
last reading stays; it never overwrites an expired or re-sign message), "Waiting for Claude Code..." on the live login, and the
existing re-authenticate message on `needsReauth`. "API Rate Limited. Try again later." is gone.

### Decisions, with reasons

- **Park deadlines are not saved across a relaunch.** The first plan saved them. A stale park that survived a relaunch is worse,
  because today a relaunch is the only way to clear a stuck card, and it costs only one extra request per account per relaunch.
  A park is also only worth keeping while it belongs to its token, and tokens change.
- **The delegated refresh (`claude auth status`, then asking again) is removed.** 13 runs, 0 recoveries, and the retry resends
  the same dead token. The live login now waits for Claude Code instead.
- **20 minutes between requests after a 401 or 429.** Measured safe for days (the 20-minute cadence from 10-11 to 06:53Z on 10-16 never
  drew a 429), and it does not depend on how many accounts are eligible. 5xx errors and network failures keep their old
  behaviour. The one short retry after a 429 with a very short `Retry-After` is also gone, to stay inside this rule.
- **`needsReauth` is set only when the server says so.** That means `invalid_grant`, a lost rotation, or a saved login that
  belonged to another account. It is NOT set by PixelSwitch's own check that refuses to spend a refresh token when the saved
  login is the same grant as the live login or another account's (`sameGrantAsAnotherLogin`, a separate outcome). Otherwise a
  healthy account would have been dropped from polling and switching, and auto-switch would have gone blind.

## Still unknown

- **Whether the server counts per token or per account.** Three natural experiments in the log favour per token: ahmed@pixelventures.ai
  read 200 on its new token at 13:53:04 after its old token took four profile 401s at 13:42 to 13:44; ahmed@bespokewoodcraftstudio.com
  read 200 at 05:08:02 on a renewed token after six failures on the old one; and again at 14:28:03 on a token renewed at 13:38.
  A per-account counter predicts a 429 in all three. This is medium to low confidence (three samples). The 14:50Z read of
  ahamade@gmail.com that was first proposed cannot settle it. The guard works either way, because it spends at most one
  request per new token. That request is also the experiment.
- **Whether profile 401s count toward the limit.** The correlation is strong (31 of 33 cases with 3 or more profile 401s drew a
  429 on the first request after the park, 0 of the cases with 2 or fewer), with one clean counterexample on 2026-10-15 at
  01:53:34. 1.9 stops sending them anyway.
- **Who revoked the two refresh grants.** ahmed@pixelventures.ai and ahamade@gmail.com were never the live login between
  10-06 and 10-16, yet their grants died (ahmed@pixelventures.ai 8.6 hours after PixelSwitch last rotated it). Something outside
  PixelSwitch on this Mac or another machine presented the grant. Candidates: a long-lived Claude Code process holding an older
  login, stale Keychain items from other config folders, or the Beeco Mac, which held ahmed@pixelventures.ai until 10-09.
  Refresh-token reuse detection would explain it and is unverified.
- **Whether Claude Code re-reads the Keychain after a 401**, and what the real Anthropic threshold and window are.
- **Whether the live-login wait can leave auto-switch blind.** In all 12 stale-live-token runs Claude Code's spending stayed
  flat, so none shows Claude Code working on an expired Keychain token. The remaining risk is a failed Keychain write by Claude
  Code. The card keeps its "Updated ... ago" label on the last reading, so the age shows.

## What the founder can do

- Nothing is needed for 1.9 to help. After it installs, a card with an expired live login says it is waiting for Claude Code and
  keeps its numbers; it reads again the next time any Claude Code session runs on that account.
- An account whose refresh grant the server refused shows the re-authenticate message and stops being polled. Press its ↻
  once. That also makes it the live login, so pick the account you want to end up on last.
- After 1.9, count 429s in the log for 48 hours. The expectation is zero.

## Review fixes (2026-10-16)

- **A needs-reauth flag with no token no longer takes the live login.** A flag raised after a saved login was removed
  (the "belongs to another account" case), or restored after a relaunch, holds no token. It used to adopt the first token
  it saw, and if that was a healthy live login the active account lost its reading until Claude Code renewed it. Now an
  active account clears such a flag, and a saved login still adopts its token as before.
- **A switch renews a refused saved login.** After a 401 on the profile lookup the cool-down answers first, so the switch
  now asks the guard whether that exact token was refused (`wasRejected`) and renews it. An expired or refused target that
  sits inside a park or cool-down is renewed too (a POST to the token endpoint, outside both limits).
- **An offline or failing token endpoint says so.** A renewal that got no verdict (no connection, 5xx, 429) is its own
  outcome, `unreachable`, and the card shows the same "Can't reach Anthropic" line as a usage request would, keeping the reading.
- **The same-grant refusal is a tested function** (`BackupRefreshOutcome.localRefusal`), so the test now fails if the
  local guard ever returns the server's verdict.
