## B. The Accounts-tab re-auth button and the flow

- **View**: `PixelSwitch/Views/AccountSwitcherView.swift:209-217`: `Button { appState.reauthenticateAccount(account) } label: { Image(systemName: "arrow.triangle.2.circlepath") ... .foregroundStyle(.limitWarn) }`, `.buttonStyle(.plain)`, `.help("Re-authenticate (fix stale token)")` (localised key at `en.lproj/Localizable.strings:99`). It is shown on every row, signed in or not, with no disabled state while `isLoggingIn`. There is no re-sign button in Settings (`SettingsAccountRow.swift` has none).
- **Action**: `AppState.reauthenticateAccount(_ account: Account)` `AppState.swift:570-577` -> `startSignIn(.reauthenticate(accountId:, email:))` (:520-565) -> on throw `reportSignInStartError` (:586-603: `.claudeUnavailable` sets `errorMessage`; `.busy` sets "A sign-in is already in progress." and posts `.pixelswitchShowSignIn`, or "A switch is in progress...").
- **What `startSignIn` does**: `SignInGate.decide(claudeAvailable:isSwitching:isLoggingIn:current:)` (busy/unavailable gate) -> `isLoggingIn = true`, `errorMessage = nil` -> builds `SignInSession(purpose:launch:runner:scheduler:log:complete:onFinish:)` (`Services/SignInSession.swift`; launch from `claudeService.signInLaunch()`, runner `ProcessSignInRunner`) and stores it in `currentSignIn` -> `backUpBeforeSignIn(for:)` (:605-626: for a reauth it backs up the current ACTIVE account first if it is a different account) -> `session.start()` runs `claude auth login` with `BROWSER` pointed at the per-sign-in capture helper (`SignInLinkCapture.swift`, `SignInProcess.swift`, `ClaudeProcessEnvironment.swift`), shows both links with Open / Open in / Copy; nothing opens by itself. On exit 0, `completeSignIn` (:629-640) waits 1 s then `finishReauthentication(accountId:expectedEmail:)` (captures the fresh credentials for that account; clears the flag through `noteCredentialChanged`).
- **Window**: `Services/SignInWindowController.swift`. It observes `AppState.$currentSignIn`; a new session shows a floating `NSPanel` (utility window, `isFloatingPanel`, level `.floating`, `hidesOnDeactivate = false`, 460x380) hosting `Views/SignInView.swift` (`.reauthenticate(_, let email)` copy at :44). `show()` calls `NSApp.activate()` then `makeKeyAndOrderFront` (:93-94). The panel is deliberately NOT part of the popover. Closing it while running cancels the sign-in; success/cancel hides it; failure stays open (:68-77, :128-144). It is created in `PixelSwitchApp.swift:32` (`@State private var signInWindowController`).
- **Can the same action be called from the card? Yes, unchanged.** `UsageDashboardView` already has `@EnvironmentObject appState`. A `Button { appState.reauthenticateAccount(account) }` inside the card works exactly as it does in `AccountSwitcherView`. Nothing new is needed in `AppState`.
- **Popover and focus constraints**
  - `Services/StatusItemController.swift:5-108`: the popover is an `NSPopover` with `behavior = .transient` and `animates = false` (:66-68), NOT SwiftUI `MenuBarExtra` (CLAUDE.md still says MenuBarExtra in places; `StatusItemController.swift:7-8` explains the switch). A transient popover closes when another window becomes key. So clicking the new button will open the sign-in panel and the popover will close as the panel takes focus. That is the same behaviour the Accounts-tab button has today and is what the code comment at `SignInWindowController.swift:8-9` expects ("the popover closes the moment the user switches to a browser, and the sign-in must survive that"). While the sign-in runs, `AccountSwitcherView.addAccountButtons` (:259-284) shows "Signing in..." with a "Show sign-in window" button; the Usage tab has no equivalent (it only disables double-click switch via `canSwitch`, `UsageDashboardView.swift:349-351`).
  - Activation policy: `LSUIElement: true` (`project.yml:42`), so the app is an accessory. `NSApp.activate()` is what brings the sign-in panel forward; no policy switch exists or is needed. `HiddenWindowView.swift` is the keepalive window workaround for SwiftUI scenes.
  - The Settings gear does `NSApp.activate(ignoringOtherApps: true)` then posts `.pixelswitchOpenSettings` (`MainMenuView.swift:366-370`), the pattern for opening any window from the popover.
  - A card is a double-click-to-switch surface (`UsageDashboardView.swift:302-306` `.onTapGesture(count: 2)`), and the whole card is `.contentShape(Rectangle())`. A real `Button` inside it is safe: the file already does this for Retry (`usageErrorActions` comment :366-368: "Real buttons, so they never count toward the card's double-click-to-switch"). Use `.buttonStyle(.borderless)` / `.focusable(false)` as Retry does (:388-389).
  - The button should be disabled (or hidden) while `appState.isLoggingIn` or `appState.switchingTo != nil` (as `canSwitch` does), otherwise a second click throws `.busy` and only sets `errorMessage`.
- **Remote control / CLI / MCP re-auth (keep consistent)**
  - Mac: `ControlAPI.swift:118-130`: JSON-RPC method `accounts.signIn.start` with `SignInStartParams` (`ControlProtocol.swift:299-306`; `account` given -> `purpose = .reauthenticate(accountId:, email:)`, else new account), plus `accounts.signIn.status`, `.submitCode`, `.cancel` (`ControlProtocol.swift:275-278`). It goes `ControlAPI` -> `AppController.startSignIn(_:open:)` -> `AppState.startSignIn`, i.e. the same function the button calls, so a card button is automatically consistent. `SignInInfo.purpose` is `newAccount` or `reauthenticate` (`ControlProtocol.swift:353-357`, `ControlAPI.swift:430-450`); `RemoteControlService.swift:153-174` emits `signInChanged`. The `pixelswitch` CLI and its MCP server (`PixelSwitchCLI/CLIRunner.swift`, `MCPServer.swift`) wrap that method. No protocol change is needed for a UI-only button.
  - Linux: `linux/pixelswitch/control_api.py:84-96` implements the same method; the GTK Settings accounts window already has a per-account "↻ Re-sign" button that gains the `suggested-action` style when `gui/model.needs_resign(info)` is true (`linux/pixelswitch/gui/settings_accounts.py:51-63, 143-146`; `gui/model.py:52, 162-167`).

## C. The plan chip

- **Drawn at**: `Views/UsageDashboardView.swift:474-476` (card), `Views/MainMenuView.swift:265-267` (popover header, active account). Both call `Badge(text: sub, color: .brand)`; `Views/Components/Badge.swift:4-16` is `Text(text).font(.caption2.weight(.semibold)).foregroundStyle(.textOnFill).padding(AppStyle.badgeHPadding=6, badgeVPadding=2).background(color, in: Capsule())`. The "Active" chip is the same view with `.green`.
- **Colour source**: `Color.brand`, a LITERAL in `Models/BrandColor.swift:8` (`Color(red: 0xE8/255, green: 0x6D/255, blue: 0x45/255)`, #E86D45, NOT adaptive: same in light and dark). Text on it is `Color.textOnFill` = #111111 (:114, 6.0:1 on the coral). Every plan renders in that one colour today, because the call site hard-codes `.brand` and nothing maps a plan to a colour. "Orange Ultra on every card" is therefore by construction, not by detection.
- **How the tier is determined** (`Models/AccountPlan.swift`, 280 lines, pure Foundation, unit-tested by `Tests/UnitTests/AccountPlanTests.swift`)
  - `enum AccountPlan { pro, max5x, ultra, other(String), unknown }` (:27-36).
  - `AccountPlan.resolve(subscriptionType:planTier:planDisplayName:sessionObserved:)` (:61-75): if subscription type is nil or "max": tier in `max5xTiers` -> `.max5x`; else if not `sessionObserved` and tier in `ultraTiers` or display name "ultra" -> `.ultra`. Then `guard let type else .unknown`; `type == "pro" ? .pro : .other(type)`. So team/enterprise/anything else becomes `.other("team")`, and a Max whose tier is unrecognised becomes `.other("max")`.
  - `badgeText(subscriptionType:)` (:85-88): "Ultra" for `.ultra`, else the subscription type with first letter upper-cased ("max" -> "Max", "pro" -> "Pro", "team" -> "Team", "enterprise" -> "Enterprise"); nil when there is no subscription type. `Account.displaySubscriptionType` (:163-165) is the one string every UI site uses (popover header, card, Accounts row, widget, CLI/MCP).
  - **Raw inputs**: `Account.subscriptionType` and `Account.planTier` (`Models/Account.swift:37, 65`), both written from `claude auth status` JSON (`AuthStatus.subscriptionType`, `AuthStatus.planTier`, `Account.swift:156-190`; `ClaudeService.getAuthStatus` :204-214). Write sites: `AppState.swift:485-487` (addAccount), `:722-724` (loginNewAccount new), `:825-826` (existing, merged via `AccountPlan.updatedTier`), `:2674-2675` and `:2687-2689` (updateActiveAccount on each refresh). Fallback fill for accounts without a tier: `backfillPlans` (`AppState.swift:2160-2190`, `PlanBackfillLedger` :248-279) reads the saved login's `claudeAiOauth.rateLimitTier`, else the account block's `organizationRateLimitTier`, else the canonical 20x tier when `planDisplayName` is "Ultra" (`AccountPlan.tier(fromCredential:oauthAccount:)` :105-115; reads only those fields, never the token).
  - **Server fields**: the app does NOT read a plan from any HTTP endpoint. `/api/oauth/profile` is used only for identity (`account.uuid`, `account.email`, `ClaudeService.swift:323-370`); `/api/oauth/usage` carries no plan field. The plan comes from the Claude Code CLI (`claude auth status` prints `subscriptionType` and `planTier`) or from the saved login (`rateLimitTier`) and `~/.claude.json` `oauthAccount`.
  - **Values the code knows**: subscriptionType: "max", "pro", anything else lower-cased (team, enterprise ...). Tiers: `max_20x`, `default_claude_max_20x` (Ultra); `max_5x`, `default_claude_max_5x` (Max 5x); recognised-for-merge also `pro`, `default_claude_ai` (`recognisedTiers` :120). Vague CLI tiers: `max_other`, `other`, or an unknown string from a newer `claude` (the comment at :117-130 says `claude` prints `max_other` for a Max login whose saved tier is missing or new). `planDisplayName` "Ultra" is also honoured. There is no `.team`/`.enterprise` case: those are `.other("team")`, `.other("enterprise")`. Chip text for Max 5x is "Max", for Pro "Pro".
  - **Fallback when unknown**: `.unknown` has `hasSessionLimit == true` and a nil badge when `subscriptionType` is nil (no chip drawn: `if let sub = account.displaySubscriptionType`). A nil tier keeps the 5-hour limit and the plain "Max" chip. A new colour mapping needs a default for `.other(_)` and `.unknown`.

## D. Usage fetch (Weekly, Fable, Extra usage)

- **Endpoint**: `GET https://api.anthropic.com/api/oauth/usage` (`Services/ClaudeService.swift:268-307`, `getUsageLimits(accessToken:)`). Headers: `Authorization: Bearer <access token>` and `anthropic-beta: oauth-2025-04-20`. `URLSession.shared`, 200 required; non-200 maps through `UsageRequestError.from(status:body:retryAfter:)`; a 403 logs only the first 200 characters of the body (:292-295) and a 200 logs only the numbers (`session=..., weekly=..., fable=...`, :302). Decoded with a plain `JSONDecoder()` and the model in `Models/UsageData.swift`. Every call goes through `UsageRequestGuard` first (a refused token is never resent; see handover gotcha "A 429 with Retry-After 3600...").
- **Top-level keys decoded** (`UsageAPIResponse`, `UsageData.swift:5-58`): `five_hour`, `seven_day`, `seven_day_oauth_apps`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_cowork`, `iguana_necktie` (each a `UsageWindow?`), `extra_usage` (`ExtraUsage?`), `limits` (lenient list of `UsageLimit`).
  - `UsageWindow` (:148-155): `utilization` (Double, percent used 0-100), `resets_at` (ISO 8601, with or without fraction).
  - `ExtraUsage` (:231-243): `is_enabled`, `monthly_limit`, `used_credits`, `utilization`. The card draws only `is_enabled` as "On"/"Off" (`extraUsageRow`, `UsageDashboardView.swift:503-522`); the other three are decoded and exposed over the control API (`Control/ControlAPI.swift:297`) but not drawn.
  - `UsageLimit` (:64-115): `kind`, `group`, `percent`, `severity`, `resets_at`, `scope.model.{id, display_name}`, `is_active`. Fable = the `limits` entry with `(kind == "weekly_scoped" || group == "weekly")` and a model display name and a percent (`isModelWeekly` :102-104). **The code does not check `is_active`** when choosing it.
  - **Weekly** = `seven_day` (`usageBars` :488). **Fable** = `usage.modelWeeklyLimits` (:494-500). Both rows say `"<100 - utilization>% left"`; the reset text comes from `resets_at` via `UsageWindow.resetTimeString` (a weekday/clock time above 24 h).
- **Fields the app ignores that look related to resets/credits** (observed in Claude Code's own cache of the same endpoint, `~/.claude.json` `cachedUsageUtilization.utilization`, fetched 2026-11-19 for the active account; also described in `docs/investigations/2026-10-24-linux-and-split-thresholds/recon/laptop.md` section 5.3 and `recon/usage.md` section 2.1):

  - Inside `extra_usage`: `currency` ("USD"), `decimal_places`, `disabled_reason` ("out_of_credits" here), `user_disabled`, `spend_limit_reached`, `credits_ever_enabled`, `daily`, `weekly` (both null). Values here: `is_enabled: false`, `monthly_limit: 4000`, `used_credits: 0`, `utilization: 0`.
  - New top-level `spend`: `used{amount_minor,currency,exponent}`, `limit{...}`, `percent`, `severity`, `enabled`, `disabled_reason`, `cap{money, credits{amount_minor,exponent}}`, `balance`, `auto_reload`, `disclaimer`, `can_purchase_credits`, `can_toggle`.
  - `weekly_scoped_shares: [{limit_index, used_percent_of_weekly, allowance_percent_of_weekly}]` (here `allowance_percent_of_weekly: 50` for the Fable entry) and `member_dashboard_available`.
  - In `limits`: the same account lists a `weekly_all` entry (`kind: weekly_all`, `group: weekly`, `scope: null`, `is_active: true`) and a `weekly_scoped` Fable entry with `is_active: false`.
  - Null-valued codename windows (all null for this account, purpose unknown, nothing in the repo names them): `seven_day_omelette`, `tangelo`, `omelette_promotional`, `nimbus_quill`, `cinder_cove`, `copper_kite`, `brass_thimble`, `harbor_lantern`, `maple_sundial`, `wattle_ember`, `promo_credits`, `amber_ladder`, `granite_teacup`, `amber_cistern`, `amber_cistern_offer`, `juniper_tide`, `cedar_ember`, `starry_waterfall`, `amber_gauge`, `pace`, `indicator`, `seven_day_breakdown`. `promo_credits`, `omelette_promotional`, `amber_cistern_offer` and `pace` are the ones whose names suggest promotions or "limit resets"; they are null for this account today, so nothing about their shape is known. A raw full response is NOT logged by the app (only numbers; on a 403 the first 200 characters), so to see them live someone must capture a real response (Claude Code's `cachedUsageUtilization` is the free, no-extra-request source).
  - The app has a separate hand-made promo mechanism for "double usage" (`Models/DoubleUsagePromo.swift`, banner in `MainMenuView.swift:106-109`), not driven by API fields.

## E. Theme and design system

- No asset-catalog colours: `PixelSwitch/Resources/Assets.xcassets` holds only `AccentColor`, `AppIcon`, `MenuBarLogo`. Every colour is a Swift token in `PixelSwitch/Models/BrandColor.swift`.
- Pattern: `Color.adaptive(light:dark:)` (:19-24; an `NSColor(name:nil, dynamicProvider:)` choosing on `bestMatch(from: [.darkAqua, .aqua])`) with `rgb(0xRRGGBB)` literals. Examples: `cardFill` (:74), `textSecondary` (:110), `textOnFill` = near-black #111111 and NOT adaptive (:114), `brandText` (:117), `costGreen` (:120), `limitWarn` (:128), `limitCrit` (:129), `activeAccountRing` (:91), `subtleBrand` (:134).
