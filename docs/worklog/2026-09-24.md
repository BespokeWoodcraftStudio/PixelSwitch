## 05:07 PDT · WL-2026-09-24-001 · Two-part version numbers (1.1, 1.2, 2.0)

**Type:** decision · **Status:** done

### What
Release versions are now two-part: 1.1, 1.2, 1.3, then 2.0, 2.1. scripts/release.sh, .claude/commands/release.md and AGENTS.md were changed to enforce it. The next release is 1.1 (not 1.0.17).

### Why
Founder, 2026-09-24: "I don't like the version number, its too long. I prefer things like 1.0, 1.1, 1.2, etc. Then version 2.0, 2.1, etc."

### How
- release.sh: `minor` gives X.(Y+1), `major` gives (X+1).0, `patch` removed; an explicit version must match ^[0-9]+\.[0-9]+$ (1.1.1 and 1.0.17 are rejected). From the current 1.0.16, `minor` gives 1.1.
- release.md: dropped the patch-release cumulative-notes rule, since there are no patches; examples and tag formats updated to vX.Y.
- Tested the bump and validation logic in isolation (1.0.16 minor -> 1.1, 1.9 major -> 2.0, 1.1.1 rejected). Did not run a real release.

### Outcome
Tooling ready for `./scripts/release.sh minor`, which produces v1.1.

### Lessons
- Sparkle orders updates by the build number (CFBundleVersion, sparkle:version), which is a monotonic integer (21 -> 22), so moving the display version from 1.0.16 to 1.1 does not confuse updates.
- CI takes the appcast shortVersionString from the tag (`${GITHUB_REF_NAME#v}`), so a v1.1 tag needs MARKETING_VERSION "1.1"; release.sh keeps them in sync.

### Follow-ups
1. Founder says "go" to cut 1.1 (the first notarized release; also the first run of the Sparkle EdDSA/appcast steps with a signed DMG).
2. After it ships, update the installed 1.0.16 through Sparkle Check for Updates and confirm it installs cleanly.

## 13:10 PDT · WL-2026-09-24-006 · Remote control for AI: design started, four decisions with the founder

**Type:** design · **Status:** wip

### What
Founder asked for a way for an AI on another Mac to control PixelSwitch on this one (switch accounts, add accounts, change settings, monitor usage), as a CLI, or an API or MCP if better. Classified as architectural (new subsystem with security implications). Mapped the app's capability surface and put four decisions on a page for the founder.

### Why
Nothing may be built before the design and written spec are approved. Standing rule: founder questions go on an HTML page, not in chat.

### How
Read-only survey of the app (Explore agent), then docs/decisions/pixelswitch-remote-control-2026-09-24.html from the founder-questions template. Rendered at 1920x1080 in light and dark, Copy button tested (pasted block correct), no console errors.

Facts the design rests on:
- AppState is a @MainActor ObservableObject; its actions (switchTo, addAccount, loginNewAccount, removeAccount, updateAccountLabel, reauthenticateAccount, refresh) return Void and report only via published state and errorMessage. A control layer needs result-returning wrappers.
- No external control exists. The pixelswitch:// URL scheme is registered in project.yml but has no handler. The main app is not sandboxed and has no network entitlements, so it can host a local Unix socket.
- No AppState published property holds a token; tokens live in keychain services "Claude Code-credentials" and "ai.pixelventures.pixelswitch.backups". An API must expose only AppState-level data, never KeychainService/ClaudeService credential methods.
- Adding a NEW account runs `claude auth login`, which opens a browser on this Mac and needs a human to sign in; an AI can only start it. "Add Current Account" imports whoever `claude` is already signed in as.
- Settings inventory: refreshInterval, transcriptLookbackHours, autoSwitchEnabled/Threshold/OnFable, maskEmailAddresses, colorCodeAccounts, appLanguage, launch at login (SMAppService), menu bar modules and colours, lowRemainingWarningThreshold, claudeBinaryPathPreference. Not GUI-settable: auto-switch hysteresis and cooldown. showInDock is a dead key.
- Tests are a swiftc harness (Tests/run-unit-tests.sh, 122 checks); AppState is not in it, so the new protocol/command layer must be kept pure to be testable.

### Outcome
Recommended design, awaiting the founder's answers: a `pixelswitch` CLI shipped inside the signed app, plus `pixelswitch mcp` (stdio MCP server) from the same binary, both talking to the running app over a user-only Unix socket; the other Mac reaches it over whatever already runs commands here (SSH), so no network listener; a master switch in Settings, off by default, with levels (read-only, control, everything); tokens never cross the socket.

### Decisions pending (page: docs/decisions/pixelswitch-remote-control-2026-09-24.html)
1. How the other Mac reaches this one (decides whether a network listener is needed). 2. Permission levels. 3. How an AI may add accounts. 4. Shell commands only, or plus MCP mode.
Defaults if unanswered are on the page and are the recommended options.

### Follow-ups
1. Founder pastes the answers back; record them verbatim here.
2. Write the spec to docs/superpowers/specs/2026-09-24-remote-control-design.md, self-review, founder approves it.
3. Then writing-plans; only after that any code.
4. Decided without asking (put in the spec): CLI installed by a Settings button linking into ~/.local/bin (no admin password); CLI launches the app if it is not running; usage monitoring through a `usage` command and a streaming `watch`; the CLI must be added to the CI nested-binary signing list in build.yml.
