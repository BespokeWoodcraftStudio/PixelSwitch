## 05:07 PDT · WL-2026-09-24-001 · Two-part version numbers (1.1, 1.2, 2.0)

**Type:** decision · **Status:** done

### What
Release versions are now two-part: 1.1, 1.2, 1.3, then 2.0, 2.1. scripts/release.sh, .claude/commands/release.md and AGENTS.md were changed to enforce it. The next release is 1.1 (not 1.0.17).

### Why
Founder, 2026-09-24: "I don't like the version number, its too long. I prefer things like 1.0, 1.1, 1.2, etc. Then version 2.0, 2.1, etc."

### How
- release.sh: `minor` gives X.(Y+1), `major` gives (X+1).0, `patch` removed; an explicit version must match ^[0-9]+\.[0-9]+$ (1.1.1 and 1.0.17 are rejected). From the current 1.0.16, `minor` gives 1.1.
- release.md: dropped the patch-release cumulative-notes rule, since there are no patches; examples and tag formats updated to vX.Y.
- Tested the bump and validation logic in isolation (1.0.16 minor -> 1.1, 1.9 major -> 2.0, 1.1.1 rejected). Did not run a real release.

### Outcome
Tooling ready for `./scripts/release.sh minor`, which produces v1.1.

### Lessons
- Sparkle orders updates by the build number (CFBundleVersion, sparkle:version), which is a monotonic integer (21 -> 22), so moving the display version from 1.0.16 to 1.1 does not confuse updates.
- CI takes the appcast shortVersionString from the tag (`${GITHUB_REF_NAME#v}`), so a v1.1 tag needs MARKETING_VERSION "1.1"; release.sh keeps them in sync.

### Follow-ups
1. Founder says "go" to cut 1.1 (the first notarized release; also the first run of the Sparkle EdDSA/appcast steps with a signed DMG).
2. After it ships, update the installed 1.0.16 through Sparkle Check for Updates and confirm it installs cleanly.

## 05:41 PDT · WL-2026-09-24-003 · Removed the old CCSwitcher from the founder's Mac

**Type:** chore · **Status:** done

### What
Deleted the original CCSwitcher from the founder's machine: the two backup app copies in ~/app-backups (CCSwitcher-1.12.0-stock.app and -bws.1.app), ~/Library/Application Support/CCSwitcher, its three log files, the widget container me.xueshi.ccswitcher.widget and the old App Group container 584KQTRF3B.me.xueshi.ccswitcher.

### Why
Founder: "get rid of the old CC switcher. I don't need it anymore. We have our own version." Its stock backup copy was still registering a "CCSwitcher Widget" beside PixelSwitch's in the desktop widget gallery.

### How
Checked first that PixelSwitch holds its own data: ai.pixelventures.pixelswitch.accounts, its own keychain backups service, didImportLegacySettings set, the old prefs domain empty, ~/.ccswitcher already gone. Then killed the old widget process and removed the paths above by literal path. Left every PixelSwitch-* backup in ~/app-backups untouched.

### Outcome
`pluginkit` lists no CCSwitcher widget. A first pass missed five small leftovers (Application Scripts x2, HTTPStorages x2, Caches) which were removed in a second pass; after that nothing named CCSwitcher remained under ~/Library. PixelSwitch 1.1 kept running.

### Lessons
- A stock app copy sitting in any folder (not just /Applications) is enough for macOS to register its widget extension. Move backups out of the scanned tree (zip them) if a widget should not show.
- Do not run `pgrep -lf` on this Mac: it prints full process environments, including API keys, for the Cursor helper processes. Use `pgrep -x` or `pgrep -l` without -f.

### Follow-ups
1. The migration code in LegacyMigration.swift and KeychainService.swift still reads the old CCSwitcher locations for people upgrading from it. Harmless for the founder; remove only if no one else migrates from CCSwitcher.
2. Founder may rotate the OpenRouter, Gemini, 21st and API_TOKEN keys that appeared in an earlier tool output.
