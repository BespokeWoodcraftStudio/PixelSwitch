## 08:43 PDT · WL-2026-09-26-001 · 1.3: Update automatically (Settings → About), released and verified

**Type:** feature · **Status:** done · **Tags:** updates,sparkle,release

### What
New checkbox **Settings → About → Update automatically**, also available as `updates.automatic` from `pixelswitch` and MCP.
- On: Sparkle checks by itself every 6 hours, downloads in the background, and PixelSwitch relaunches into the new version by itself, but only when no account switch, login or sign-in is running.
- Off (the default): the old behavior, a background check that asks before installing.

Released as 1.3 (build 24, tag v1.3, CI run 36252647560).

### Why
Founder, 2026-09-26: "add an auto-update feature to the product so that someone could check the box, and it automatically checks for updates and updates automatically."

### How
- PixelSwitch/Services/UpdateChecker.swift:
  - It is now an NSObject and the SPUUpdaterDelegate.
  - `setInstallsAutomatically(_:)` sets `automaticallyChecksForUpdates` (when on) and `automaticallyDownloadsUpdates`; Sparkle persists the value as SUAutomaticallyUpdate.
  - `updater(_:willInstallUpdateOnQuit:immediateInstallationBlock:)` returns true and runs the block as soon as `isBusy()` is false. Otherwise it retries every 60 s, holding the block in `pendingInstall`, not captured in the timer, to satisfy Swift 6 Sendable checking.
- PixelSwitch/Services/AutoUpdatePolicy.swift: pure `mayInstallNow(isSwitching:isLoggingIn:signIn:)`; unit-tested in Tests/UnitTests/AutoUpdateTests.swift.
- PixelSwitchApp wires `updateChecker.isBusy` to AppState at launch.
- SettingKey.autoUpdate ("updates.automatic", bool):
  - SettingsStore reads and writes it through `SettingsStore.updateChecker`, set in RemoteControlService.start;
  - the CLI's SettingKeyNames includes it (a guard test caught the missing entry);
  - the MCP get_settings description names it.
- The About tab has a checkbox-style Toggle. Two new strings in all five languages (252 keys each).
- project.yml: `SUScheduledCheckInterval: 21600`. README: an "In-App Updates" sentence.

### Outcome
- 516 of 516 unit tests pass; the type-check is clean with no warnings.
- Branch CI run 36252414920 was green, and the branch was fast-forwarded into main.
- Released through the fixed release.sh, which found the tag-push build and started no second one. The main-push build was cancelled.
- Verified with scratchpad verify-release.sh:
  - the release is Latest; the feed offers 1.3 (24);
  - the appcast length equals the DMG size, and the EdDSA signature verifies against SUPublicEDKey;
  - the app reports 1.3 (24) with SUScheduledCheckInterval 21600; the helper is signed (team LM3P28DNVQ); deep verify passes; spctl reports Notarized Developer ID for the app and the DMG; the ticket is stapled;
  - "Update automatically" is present in the shipped en and de strings (UTF-16: read with `plutil -p`, not grep).
- The hand-check page is updated for 1.3: card 1 updates to 1.3, and new card 2 turns the box on.

### Decisions & trade-offs
- **One checkbox, off by default**, as the founder described ("check the box"). Off keeps the old behavior, not "no checks".
- **Relaunch at once, not at quit.** A menu bar app rarely quits, so Sparkle's default (install on quit) would effectively never install. Installing never interrupts a switch, a login or a sign-in; that would cut a keychain write or a login in half.
- **Checks every 6 hours instead of daily**, for everyone, so a release reaches an auto-updating Mac the same day.
- Unticking the box while an update waits drops it; Sparkle then installs it at the next quit.

### Lessons / gotchas
- Sparkle's `willInstallUpdateOnQuit` delegate is the hook for an immediate automatic install. `@preconcurrency` on the SPUUpdaterDelegate conformance is unnecessary (the compiler warns it has no effect).
- The real end-to-end proof (1.3 installing 1.4 by itself) needs the next release. Until then only the pieces are verified.
- Compiled .strings in the app bundle are UTF-16, so grep finds nothing; use `plutil -p`.

## 13:22 PDT · WL-2026-09-26-003 · 1.5: Manual only (0%) and per-account thresholds 1–100%, designed by workflow, reviewed, released

**Type:** feature · **Status:** done · **Tags:** auto-switch,thresholds,workflow,release

### What
Per-account auto-switch thresholds now run 0–100%. 0 is **Manual only**: auto-switch never moves you to the account; you can still switch to it yourself; while it is active it is left only at the default threshold and never early-drained. It is the named last item of the existing threshold menu, not a checkbox. 1–100% all work: below 20%, a target needs half its threshold of room. Released as 1.5 (build 26, tag v1.5, CI run 36268925156).

### Why
Founder, 2026-09-26: limits below 50%, down to 0%, with 0% meaning "disabled from being switched to", and "come up with a better idea" than a Disable-auto-switch checkbox. Verbatim, with the decisions and the rejected alternatives, in docs/decisions/2026-09-24-remote-control-answers.md.

### How
- **Design:** workflow run wf_4927df27-02c.
  - Three blind designs (clarity first, engine first, smallest change), two judges (founder lens, engine lens), and one synthesis. Both judges picked clarity.
  - The synthesis grafted the engine design's single exclusion rule (an Optional `AutoSwitchEngine.ceiling`) and the minimal design's reuse of the existing labels.
  - The full spec was in scratchpad/final-spec.json (session-scoped); its decisions are copied into the decisions record.
- **Build (single implementer, test-first, in the spec's order):**
  - AutoSwitchSettings: `accountThresholdRange` 0–100, `accountStepperRange` 1–100, `manualOnlyThreshold`, whole-number normalization, `isManualOnly`, `leaveAtThreshold`, `explanation`.
  - AutoSwitchEngine: `hysteresis`, `ceiling(threshold:room:)` = T − min(room, T/2), nil for ≤ 0, used by both rules and keepsFable; `plan()` takes a required `defaultThreshold`.
  - AccountOrder.fallback.
  - AppState: wiring and logs.
  - Control protocol 2 (`AccountInfo.manualOnly`); API range 0–100.
  - CLI: `accounts threshold <a> <1-100|default|manual>`, plus `CLIOutput.switchesAt`, `thresholdSet` and `switched`. MCP: minimum 0.
  - Views: the Settings menu, stepper, tooltip, captions and orange warning; a popover line on the Accounts row and the Usage card footer.
  - Eleven strings in five languages (259 keys each), four retired, and a parity test.
- **Review:** workflow run wf_de22bae8-d34. Four angles (engine, views and strings, remote, spec), with two skeptics per finding; 36 agents.
  - No critical or important findings survived.
  - Fixed: the tooltip's missing early-switch number (AutoSwitchSettings.explanation plus a second string); protocol 1 in the integration script and ARCHITECTURE.md.

### Outcome
- 576/576 unit tests pass; the type-check is clean for the app and the CLI.
- The branch built in Xcode on CI (run 36268236964).

  - the feed offers 1.5 (26), and the EdDSA signature verifies against the DMG;
