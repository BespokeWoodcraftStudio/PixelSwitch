## 10:40 PST · WL-2026-11-20-002 · 2.4: launch-crash fix, Limit resets per-account Chrome profile, five Settings icons, app-drawn hover labels; live launch test, records and hand-check page for the release

**Type:** fix · **Status:** partial

### What
PixelSwitch 2.4 is launch-tested, closed out and released (the release line is at the end of this entry once verified). Contents of `git log v2.3..bfd3cbe`:
- **Launch crash fixed.** The one-time clean-up of the 2.2 window's data no longer uses WebKit at all, and the trigger key is removed first and each value is read on its own, so a mixed-type value cannot crash the launch.
- **Limit resets uses a stored per-account Chrome profile choice** (`PixelSwitch/ChromeProfiles/`): a mapping account id to `directory:<Chrome directory>`, with the PixelSwitch-owned directory "PixelSwitch <email>" for an account with no choice. An explicit stored choice beats a readable Local State match. PixelSwitch never sends `--profile-email` alone. The Settings globe menu shows and sets the choice.
- **Settings account rows have five plain icons** (Switch, Re-sign, Edit label, Chrome profile globe, Remove); the "..." menu is gone.
- **Hover labels are drawn by PixelSwitch** (footer and Settings icons), not the system tooltip. Row labels stay inside their row; Automatic says what it does.
- Records: RELEASE_NOTES.md 2.4 section, this entry, the handover, the 2.4 hand-check page `docs/decisions/pixelswitch-hand-checks-2.4-2026-11-20.html` (generator `scripts/hand-checks/gen-hand-checks-2.4.py`, render script `render-hand-checks-2.4.cjs`, screenshots in `docs/evidence/2026-11-20-hand-checks-2.4/`), the Chrome finding `docs/investigations/2026-11-20-chrome-profile-email-test.md`, and the 2.3 answers file `docs/decisions/hand-check-answers-2.3-2026-11-20.md` (follow-ups marked shipped in 2.4).

### Why
The founder's report on 2026-11-20 after Sparkle installed 2.3: "i updated to the newer version and now its 100% broken, it does NOT show up in my menu bar anymore". His 2.3 hand-check answers (verbatim in `docs/decisions/hand-check-answers-2.3-2026-11-20.md`): Limit resets failed for beeco1 (a login page in a new window) and for the Bespoke Woodcraft account; the hover labels "work sometimes"; "why did you put it behind 3 dots? why not just have 3 icons?".

### How
Lanes (launch-crash, ui-icons, chrome-match) in separate worktrees merged into `lane/integration-24`, each reviewed (Sonnet first passes, an Opus final review PASS), merged to main as `bfd3cbe`; Mac tests 2467. **Live launch test before the release (now a release step):** a Debug build of `bfd3cbe` (`xcodegen generate`, `xcodebuild ... -derivedDataPath <scratch>/dd-rel24 CODE_SIGNING_ALLOWED=NO build`, BUILD SUCCEEDED) was started directly after planting the 2.3 crash trigger with a mixed-type value (`defaults write ai.pixelventures.pixelswitch ai.pixelventures.pixelswitch.claudeWeb.dataStoreIDs -dict X 00000000-0000-4000-8000-000000000001 Y -int 5`). After 45 s: process alive, no new PixelSwitch `.ips` in `~/Library/Logs/DiagnosticReports`, the key gone (`defaults read` errors "Could not find key"), the app log showed a normal launch (`[init] Loaded 7 accounts`) and `[webCleanup] forgot the saved claude.ai window list left by 2.2; removed 0 leftover data folder(s), 1 already gone, 0 left in place`, and no error line. His own app was quit first (pid 8976) and reopened afterwards from /Applications (pid 38075, version 2.3 until Sparkle installs 2.4).

Chrome finding (`docs/investigations/2026-11-20-chrome-profile-email-test.md`, Chrome 158 live): macOS blocks PixelSwitch reading Chrome's profile list (Local State); `--profile-email=<email>` finds an exact (case-insensitive) match, but for an email it cannot match Chrome silently opens the LAST-USED profile (another account's) with no picker and no error; `--profile-directory` always wins over the email and Chrome creates a missing directory. Design chosen: PixelSwitch never sends the email alone; a per-account stored directory choice, else its own "PixelSwitch <email>" directory (fresh, the founder signs in once).

### Outcome
Released as 2.4 (see the release line below once it is there). The hand-check answers for 2.4 are not in yet: the page asks for the version, the menu bar icon after a restart, the five icons, hover labels (five tries each), Limit resets for the three accounts, and the globe menu.

### Failures
- **FAILURE: 2.3 crashed on every launch for any Mac that had opened the 2.2 window.** Root cause: the first-launch clean-up called `WKWebsiteDataStore.remove(forIdentifier:)` with no web view alive, which crashed inside WebKit (crash report `PixelSwitch-2026-11-20-090543.ips`), and the key that records which data stores to clean was removed only after the call succeeded, so it crashed again on every launch. The app never reached the menu bar, and because it crashed before it could check for updates it could not update itself to a fix. Found from the founder's report above. He was unblocked by deleting the trigger key `ai.pixelventures.pixelswitch.claudeWeb.dataStoreIDs` (`defaults delete`), after which 2.3 launched. The fix is in 2.4 (no WebKit, key first). It shipped because no review or test ever launched the built app with the triggering state present: 2.3's tests called the clean-up in isolation with nothing to clean.
- **2.3's Limit resets still failed in his hands** (login page for beeco1; the Bespoke account failed; an empty "PixelSwitch <email>" profile was created for an account that had a matching profile, because the matcher could not read Chrome's profile list). Fixed in 2.4 by the stored choice.

### Lessons
- **LESSON: code on the launch path must be exercised in a real launch of the built app with the triggering state present, before every release.** Unit tests of the function are not enough. It is now a permanent step of the release ritual in `docs/SESSION-HANDOVER.md`: build, quit the user's app, plant the state, launch the binary, wait 45 s, check alive, no new `.ips`, the key gone, the log; then relaunch his app.
- A tool that works through hidden state (Chrome's profile list, which macOS blocks) must never depend on guessing it; Chrome's silent fallback to the last-used profile on an unmatched email is a wrong-account risk, so send an explicit directory or nothing.
- The system tooltip is unreliable in a menu bar popover; draw the label yourself.

### Decisions
- **NOT sending `--profile-email` alone, ever.** Reason: the live test shows an unmatched email lands in the last-used profile (another account's). Explicit `--profile-directory` is deterministic.
- **A per-account stored Chrome profile choice, with an explicit choice beating any readable match.** Reason: PixelSwitch cannot read Chrome's profile list, and a person's own choice is the most reliable truth.
- **Plain icons, not a "..." menu** (his check-5 comment). **App-drawn hover label** (his check-3 comment).
- **Unchanged and pinned by a repo-wide test: NO reset call, NO User-Agent change, NO in-app claude.ai window.** "you absolutly do not execute a reset": every reset is his own click; this release was tested without ever opening claude.ai or Chrome.
