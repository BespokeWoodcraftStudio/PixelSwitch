## 18:49 PDT · WL-2026-09-23-001 · Apple Developer account: signing prep, blocked on portal login

**Type:** infra · **Status:** blocked

### What
Founder now has an Apple Developer account. Audited what turns on Developer ID signing and notarization for PixelSwitch releases, generated a signing CSR, and opened the Apple certificate page for him.

### Why
Releases are ad-hoc signed today, so a fresh DMG install hits Gatekeeper's "could not verify" block. The CI workflow already has the full sign, notarize, staple and Sparkle sequence; it is gated on secrets that do not exist.

### How
- .github/workflows/build.yml gates on MAC_CERTS_P12_BASE64. `gh secret list` shows only SPARKLE_EDDSA_KEY is set. `security find-identity -v -p codesigning` shows 0 identities locally.
- Generated a 2048-bit RSA key and CSR with openssl in the session scratchpad (private key never enters the repo): /private/tmp/claude-501/-Users-ahamade-Documents-GitHub-PixelSwitch/5299d6d9-0918-4e20-bcb9-99a2e5f04556/scratchpad/PixelSwitchDevID.{key,csr}
- Tried to drive developer.apple.com with the Playwright MCP; refused with "Browser is already in use" because another live session holds Chrome (pid 22349) on the shared ~/.playwright-mcp/claude-cli profile. Did not kill it: it likely serves a peer session.

### Outcome
Blocked on the founder: sign in to developer.apple.com (2FA), create a "Developer ID Application" certificate, upload the CSR, download the .cer. Nothing is committed to the workflow or project.yml yet.

### Lessons
- Apple 2FA cannot be automated; only the login step needs the founder, everything after the .cer download is scriptable.
- Never free the shared Playwright profile by killing Chrome; several sessions share it.
- The Playwright MCP has no per-call isolated option; --isolated is a server startup flag.

### Follow-ups

2. Session: read Team ID from the .cer (`openssl x509 -inform DER -noout -subject`), build the .p12 with the scratchpad key and a random password, base64 it.

## 18:53 PDT · WL-2026-09-23-002 · Developer ID certificate issued; 3 of 5 signing secrets set

### What

### Why
build.yml switches on Developer ID signing when MAC_CERTS_P12_BASE64 exists, then notarizes with APPLE_ID + APP_SPECIFIC_PASSWORD.

### How
- Verified the downloaded .cer's public key matches the openssl key, built the .p12 with the Apple Developer ID G2 CA in the chain, used 3DES/SHA1 PBE so macOS `security import` reads it (OpenSSL 3 defaults do not import).
- `security verify-cert -p codeSign` succeeded on the chain; the identity shows valid in the login keychain.
- Deleted the loose key, p12 and password from the scratchpad; the login keychain is now the only copy (export from Keychain Access for a backup).
- project.yml DEVELOPMENT_TEAM deliberately left empty: CI signs with raw codesign, and setting a team would make local Automatic-signing builds demand an Xcode-signed-in account and App Group provisioning.

### Outcome
Secrets set: MAC_CERTS_P12_BASE64, MAC_CERTS_P12_PASSWORD, APPLE_TEAM_ID (plus existing SPARKLE_EDDSA_KEY). Still missing: APPLE_ID, APP_SPECIFIC_PASSWORD.

### Lessons
- HAS_APPLE_SECRETS only checks MAC_CERTS_P12_BASE64. Until APPLE_ID and APP_SPECIFIC_PASSWORD exist, ANY push to main runs the signing path and the Notarize step fails, turning CI red. Do not push to main before both are set.
- `security find-identity -v` on a throwaway keychain reports 0 valid even when the chain verifies; use `security verify-cert -p codeSign`.
