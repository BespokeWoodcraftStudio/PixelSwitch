## 2. Feature A: separate session (5-hour) and weekly (7-day) thresholds

### 2.1 Data

- `Account` gains `sessionThreshold: Double?` and `weeklyThreshold: Double?` (Swift: `var`, optional, decode-safe; absent
  in old saved JSON). Stored as whole numbers 1-100; `nil` = follow the next layer. Window values are never 0.
- `switchThreshold` keeps its meaning: the both-windows value 1-100, `0` = Manual only, `nil` = follow the default.
- Global (Mac `UserDefaults`; Linux `settings.json`): existing `autoSwitchThreshold` (base, 50-100, unset = 90) plus new
  `autoSwitchSessionThreshold` and `autoSwitchWeeklyThreshold` (50-100; absent = follow the base).

### 2.2 Resolution (one pure function per platform; names are suggestions)

```
defaults.session = clamp50to100(globalSession ?? base)      base = autoSwitchThreshold, unset/0 -> 90
defaults.weekly  = clamp50to100(globalWeekly  ?? base)

rule(account).isManualOnly = normalized(account.switchThreshold) == 0
rule(account).session = isManualOnly ? 0 : (normalized1to100(account.sessionThreshold) ?? normalized1to100(account.switchThreshold) ?? defaults.session)
rule(account).weekly  = isManualOnly ? 0 : (normalized1to100(account.weeklyThreshold)  ?? normalized1to100(account.switchThreshold) ?? defaults.weekly)

leaveAt(active).session = rule.session > 0 ? rule.session : defaults.session     (Manual only active account leaves at the defaults)
leaveAt(active).weekly  = rule.weekly  > 0 ? rule.weekly  : defaults.weekly
```

Normalisation of a window value: not a finite number -> nil; else round to whole; then clamp to 1-100.

### 2.3 Engine rules (replacing the single binding threshold; everything else in `AutoSwitchEngine` is unchanged)

Let `s`, `w` be a reading's session and weekly utilisation after the existing expiry rule (a window whose `resets_at`
is in the past is dropped; strict on the active side when the sample is retained, lenient for candidates), `f` the
Fable weekly utilisation, `ceiling(t, room)` the existing function (nil when `t <= 0`).

1. **Trigger, windows.** The active account reaches its limit when `s >= leaveAt.session` OR `w >= leaveAt.weekly`
   (a missing window cannot trigger). Report which window fired (`session` first if both) for logs and the
   `autoSwitched` event (`window` field, additive; `limit` stays `"windows"`).
2. **Trigger, Fable** (only when Fable watching is on): `f >= leaveAt.weekly`.
3. **Candidate eligibility, threshold rule, on windows:** `cs = ceiling(rule.session, hysteresis)`,
   `cw = ceiling(rule.weekly, hysteresis)`; both must be non-nil; the candidate needs at least one usable window
   reading, and every usable window reading must be under its ceiling: `s <= cs` (if s known) and `w <= cw` (if w known).
4. **Candidate eligibility on Fable:** `f <= cw` AND rule 3 holds.
5. **Early drain and no-subscription:** as today, but with `room = drainMinimumRoom` applied per window (`s <= ceiling(rule.session, 1)` and `w <= ceiling(rule.weekly, 1)`); the drain's Fable check uses the weekly ceiling.
6. **Room** (the "most room" ranking value): on windows, `min(rule.session - s, rule.weekly - w)` over the windows that
   have a reading; on Fable, `rule.weekly - f`. `keepsFable` = `f <= ceiling(rule.weekly, hysteresis)`.
7. Ranking for `mostRoom` and `resetsSoonest` is unchanged except that it uses room from rule 6; `myOrder` (Priority)
   is the candidates' order, which is the priority-sorted accounts order (D3). The tie-break in every strategy is that order.
8. **Equivalence (a hard test):** when every account's session and weekly rules are equal, every plan is identical to
   1.9's. The existing engine tests (`Tests/UnitTests/AutoSwitchRulesTests.swift`) must pass unchanged through a
   compatibility overload that takes one threshold per account and maps it to equal windows.

### 2.4 What the user sees (Mac)

- **Settings, General:** the one default slider becomes two, "Session (5-hour) default" and "Weekly default", each
  50-100. Moving one writes only its own key. (The GUI writes through the same code path as `SettingsStore`, or
  matches its rules exactly: recon `control.md` risk 12.)
- **Settings, Accounts:** each row shows, in this order: a **Priority** control (whole number 1-99 or None; shown as
  "#1"), the account, a **Session** threshold menu and a **Weekly** threshold menu. Each menu offers Default (with the
  default's number), Manual only, 10-40 in 10s, 50-100 in 5s, and the stepper for a custom whole number, as the single
  menu does today. Choosing Manual only in either menu makes the whole account Manual only (both menus read "Manual
  only"). Choosing a number while Manual only clears Manual only, sets that window, and the other window follows its
  default. Rows are always in priority order; dragging still works and renumbers (D3). Under the list, one sentence
  explains priority; if the strategy is not Priority, the D6 line and its **Use priority** button.
- The per-account help text states both windows, e.g. "Auto-switch moves you off this account at 90% of its session or
  50% of its week, and moves you to it only while it is at 89% or less of its session and 49% or less of its week."
  When the two windows are equal, today's sentence is kept word for word.
- **Menus and dashboard** (the account switcher dropdown, usage rows): show "#n" before an account's name when it has
  a priority. Any threshold marker drawn on a usage bar uses that window's own threshold.
- Strategy picker label for `myOrder`: "Priority (lowest number first)". All new and changed strings in all five tables
  (en, de, fr, ja, zh-Hans) with real translations; the key-set test must pass.

## 3. Feature B: priority numbers

- `Account.priority: Int?` (Swift `var`, optional), whole numbers 1-99. Pure helpers next to `AccountOrder`:
  `sortedByPriority(_:)` (stable), `settingPriority(_:of:in:) -> [Account]?` (nil for an unknown id or a value outside
  1-99 other than nil), `numberedInOrder(_:)` (assigns 1..N; used by `setOrder` and a drag).
- `AccountOrder.fallback(from:)` (where to go when the active account is removed) uses the priority-sorted order.
- Every code path that appends or reorders accounts leaves the array sorted (sign-in, add-current, setOrder, drag,
  setPriority, load from disk: sort on load too).

## 5. The Linux version

### 5.1 Shape

One background service owns everything that talks to Anthropic or writes a login; every face is a client of its
socket. (One process must own the usage guard and all HTTP: `usage.md`.)

| Piece | What it is | Runs as |
|---|---|---|
| `pixelswitchd` | Accounts, saved logins, Claude Code login switching, usage and profile polling behind the usage guard, saved-login renewal, auto-switch, sign-in sessions, the updater, the control socket | systemd user service `pixelswitch.service` (enabled; starts at login, and at boot with lingering) |
| `pixelswitch` | The CLI and `pixelswitch mcp`, same commands, flags, output and exit codes as the Mac CLI (`control.md` 3.x) | on demand |
| `pixelswitch-tray` | GNOME top-bar icon (StatusNotifierItem) with a menu: each account in priority order with `#n`, session and weekly %, active one checked, click to switch; Auto-switch on/off; Refresh; Settings; Sign in another account; Quit tray. Label next to the icon: the active account's session %. Live via `events.subscribe` | GTK 3 process, autostart in the graphical session |
| `pixelswitch-settings` | Settings window: Accounts (priority, session and weekly thresholds, Manual only, label, re-sign, remove with confirmation), General (auto-switch, both defaults, strategy, Fable, early switching and hours, refresh interval), Sign in (start, both links with Open and Copy, code box, status), About (version, Update automatically, Check now, where the log is) | GTK 4 + libadwaita process, opened from the tray or the app grid |

### 5.2 Paths and files (Linux)

- Claude Code's login: `~/.claude/.credentials.json` (0600, top key `claudeAiOauth`, other top keys such as `mcpOAuth`
  preserved on write). Identity: `~/.claude.json` key `oauthAccount` (opaque object; read `accountUuid`, `emailAddress`).
  `CLAUDE_CONFIG_DIR` is not honoured, as on the Mac (`ClaudeCredentialsFile.swift:22-27`); README says so.
- PixelSwitch: settings and account list in `~/.config/pixelswitch/` (`settings.json`, `accounts.json`, 0600); saved
  logins in `~/.local/share/pixelswitch/backups.json` (0600, directory 0700), same shape as the Mac's keychain item
  `{uuid: {token, oauthAccount}}`; log `~/.local/state/pixelswitch/pixelswitch.log` in the Mac log's line format;
  socket `$XDG_RUNTIME_DIR/pixelswitch/control.sock` (fallback `~/.local/state/pixelswitch/`, 0700 dir, 0600 socket, `SO_PEERCRED` uid check).
- Install: `~/.local/share/pixelswitch/app/<version>-<build>/` with a `current` symlink; `~/.local/bin/pixelswitch`
  link; `~/.config/systemd/user/pixelswitch.service`; `~/.config/autostart/pixelswitch-tray.desktop`;
  `~/.local/share/applications/pixelswitch-settings.desktop`; an icon under `~/.local/share/icons/hicolor/`.
- Every file write that holds a login is atomic (temp file in the same directory created 0600, fsync, rename).

### 5.4 Updater (Linux)

Checks `https://github.com/BespokeWoodcraftStudio/PixelSwitch/releases/latest/download/latest-linux.json` two minutes
after start and every 6 hours (a 404 is "no update", quietly). The JSON: `version`, `build`, `url` (the tarball asset),
`size`, `sha256`, `signature` (base64 Ed25519 over the tarball bytes). A newer build is downloaded, checked for size,
SHA-256 and signature (openssl 3 `pkeyutl -verify -rawin`, else the bundled pure-Python RFC 8032 verifier from
`release.md` appendix A), unpacked beside the running version, the `current` link flipped atomically, and the service
restarted when no switch or sign-in is running. The tray re-executes itself when the daemon reports a new version.
`updates.automatic` is on by default (as the Mac's since 1.4). Test hooks (`PIXELSWITCH_TEST_RELEASE_BASE`,
`PIXELSWITCH_TEST_PUBLIC_KEY`) are honoured only with `PIXELSWITCH_TEST_MODE=1`.

### 5.5 Install

`install-linux.sh` (in the repo at `linux/install.sh`, published as a release asset): fetches `latest-linux.json` and the
tarball, verifies size, SHA-256 and the Ed25519 signature with openssl (public key embedded), installs per 5.2 for the
current user only, enables and starts the service, starts the tray when a graphical session is present, and prints the
next step (`pixelswitch accounts add-current`, or Sign in from the tray). `--uninstall` removes the app and keeps saved
logins unless `--purge`. No sudo, ever. `--from <tarball>` installs a local build (for testing, still verified when a
signature is given, clearly labelled when not).

### 5.6 CI and release (Linux)

New jobs in `.github/workflows/build.yml` per `release.md` section (d): `linux-test` on `ubuntu-26.04` for every run
(Python unit and conformance tests), `linux-package` (tarball + `install-linux.sh`; signs only on a tag), and
`linux-publish` on tags only, `needs: [build, linux-package]`, uploading the tarball and `install-linux.sh` first and
`latest-linux.json` last with `gh release upload --clobber`, in its own concurrency group. It never touches
`appcast.xml` or `latest.json` and never creates or flags a release. The Linux version and build come from
`project.yml` (`MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`), the one source. `scripts/verify-release.sh` also checks
the Linux assets (present, versions match, SHA-256 matches, signature verifies with the pure-Python verifier, since the
Mac's `/usr/bin/openssl` is LibreSSL).

### 5.7 Safety on the founder's laptop (binding on every agent)
